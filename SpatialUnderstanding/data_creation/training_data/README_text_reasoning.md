# Text-Reasoning Annotation

Pipeline for taking a `no_thinking.jsonl` SFT dataset (`<answer>X</answer>` only) and producing a parallel "text-thinking" dataset where each GPT response is `<think>...</think>\n<answer>X</answer>`. The `<think>` block is generated by **Qwen3-VL-235B-A22B-Instruct-FP8** served locally via vLLM.

## Files

| Path | Role |
| ---- | ---- |
| [annotate_text_reasoning.py](annotate_text_reasoning.py) | Worker. Builds per-category prompts, calls vLLM (OpenAI-compatible), writes per-category jsonl. |
| [run_annotate_text_reasoning.sh](run_annotate_text_reasoning.sh) | Slurm sbatch. Boots the 235B vLLM server on the allocation, then runs the worker. |
| [text_reasoning_prompts/](text_reasoning_prompts/) | One Python module per category (`counting`, `anchor`, `relative_distance`, `spatial`, `perspective_taking`) plus shared `common.py`. The annotator dispatches on the id prefix and only loads that module's in-context examples. |

## Prompt design (and what changed)

The model receives the **two camera images** + a category-specific text prompt. The prompt has three parts: a category-specific `INSTRUCTIONS` block, one or two in-context examples, and a `[scene metadata]` block built from the V4/V5 normalized dataset row + per-scene `visible_objects_with_descriptions.json` and `cameras.json`.

The recent revisions tightened the prompt around two failure modes we hit on a 200-row dev sample.

### 1. Oracle vs. trace separation

Raw oracle quantities (angles in degrees, distances in metres, count fields like `difficulty_int` / `difficulty_sum`) are **kept** in the metadata block — they are how the annotator lands on the right letter — but each is tagged `oracle — do NOT cite`. The `<think>` trace must reason from VISUAL cues only (where an object appears in each frame, foreground/background, same-object-from-two-vantages), so a future student model that has only the two images can plausibly reproduce the reasoning. Direction words and qualitative depth comparisons are allowed; raw numbers are not.

### 2. CASE A / CASE B branching for spatial + perspective_taking

Empirically ~56% of `spatial_orientation` rows have the target object **not visible** in the POV camera — the asker is asking about an off-screen object the partner camera can see. The earlier "describe where the target sits in the POV frame" prompt collapsed on the majority case.

Both `spatial.py` and `perspective_taking.py` now branch on POV-visibility, and `text_reasoning_prompts/common.py` gained the helpers used to build the new metadata blocks:

- `bbox_to_placement(bbox_2d)` → maps a normalized 2D bbox to qualitative placement labels (`mid centre-right`, `upper left edge`, …).
- `angle_in_cam_frame(T_world_to_cam, world_xyz)` → reproduces the dataset's angle convention (verified: 20/20 spatial rows match within ±5° using world-to-camera `T` and `atan2(p_cam[0], -p_cam[2])`).
- `relative_camera_pose(T_pov, T_other)` → returns where the OTHER camera sits relative to POV (8-way bucket) and a coarse facing label.
- `find_objects_by_category`, `shared_landmarks` → for triangulating off-screen targets.

**CASE A** (target visible in POV) — metadata cites the target's placement in each frame and the trace translates POV placement to a direction word.

**CASE B** (target NOT visible in POV) — metadata cites the target's placement in the OTHER image, lists up to 2 shared landmark objects (visible in both images, ranked by POV bbox area), and a relative-camera-pose hint. The trace uses these to argue which side of the POV camera the target lies on, including "behind".

### 3. POV-mapping fixes (verified empirically)

`cameras.json` `T` is **world-to-camera** (not camera-to-world). The dataset's angle is computed as `(degrees(arctan2(p_cam[0], -p_cam[2])) + 360) % 360` with 0=front, 90=right, 180=behind, 270=left.

| Category | POV camera |
| -------- | ---------- |
| `spatial` | `user_1_question` set ⇒ image 1 (`camera_0_0`); `user_2_question` set ⇒ image 2 (`camera_1_0`). |
| `perspective_taking` | `asking_to=agent_1` ⇒ image 2 (`camera_1_0`); `asking_to=agent_2` ⇒ image 1 (`camera_0_0`). The `angle` field is from this requested-POV camera; `other_agent_angle` is the asker's own view (irrelevant). |

The previous `perspective_taking.py` was reading `other_agent_angle` as the POV angle — wrong field. 20/20 PT rows now match using `angle` with the table above.

### 4. Asking-agent / partner framing dropped

Both images go to the same model, so the prompts use neutral "image 1 / image 2" wording in the metadata and traces. The original question text in some rows still says "your partner's perspective" — the metadata block resolves which image that maps to.

## Quick start

```bash
# Single-shard smoke run (50 rows). Boots vLLM on the allocation.
MAX_SAMPLES=50 sbatch SpatialUnderstanding/data_creation/training_data/run_annotate_text_reasoning.sh

# Full run, 8 shards in parallel (one sbatch array task per shard).
TOTAL_SHARDS=8 WORKERS=8 sbatch --array=0-7 \
    SpatialUnderstanding/data_creation/training_data/run_annotate_text_reasoning.sh
```

Useful overrides (env vars on the sbatch line):

| Var | Default | Meaning |
| --- | ------- | ------- |
| `INPUT` | `.../no_thinking.jsonl` | Source SFT jsonl. |
| `OUTPUT_DIR` | `.../text_thinking` | Where per-category jsonls land. |
| `TOTAL_SHARDS` | `1` | Number of shards (set with `--array=0-N-1`). |
| `WORKERS` | `4` | Concurrent requests per shard. |
| `MAX_SAMPLES` | unset | Cap each shard for a smoke test. |
| `TEMPERATURE` | `0.4` | Sampling temperature. |
| `MAX_TOKENS` | `1024` | Per-response cap. |
| `VLLM_PORT` | `8765` | Port the local vLLM listens on. |
| `NO_RESUME=1` | unset | Force re-annotate everything (default resumes). |

## Smoke test the prompt without launching the model

```bash
python SpatialUnderstanding/data_creation/training_data/annotate_text_reasoning.py \
    --dump_prompt_for spatial
```

Valid categories: `counting`, `anchor`, `relative_distance`, `spatial`, `perspective_taking`. Prints the SHARED system + the full per-category user prompt for the first matching row in `INPUT` and exits — no LLM call.

To inspect a CASE A and a CASE B row for `spatial` / `perspective_taking` side-by-side, see [`/tmp/smoke_test_prompts.py`](file:///tmp/smoke_test_prompts.py) (one-shot dev script — re-create as needed).

## Outputs

```
text_thinking/
├── counting.jsonl              # rows where <answer> matched GT
├── anchor.jsonl
├── relative_distance.jsonl
├── spatial.jsonl
├── perspective_taking.jsonl
├── counting_failed.jsonl       # GT mismatch even after one stricter retry
├── anchor_failed.jsonl
├── ...
```

Each row in the per-category `*.jsonl` mirrors the `no_thinking.jsonl` schema — `{conversations, image[2], id}` — but the `gpt` turn is `<think>...</think>\n<answer>X</answer>`. Re-running the sbatch resumes from whatever ids are already present.

## Validation / sanity checks

- **Camera convention** (must pass before annotating): the script `/tmp/check_camera_axis.py` (re-create as needed) loads 20 spatial rows, projects each candidate target's world centroid into the POV camera using world-to-cam `T`, and asserts the computed angle matches `row["angle"]` within ±5°. Currently 20/20.
- After a run, eyeball traces from `spatial.jsonl` and `perspective_taking.jsonl`: they should NOT cite degrees/metres/oracle field names, and CASE B traces should explicitly mention a shared landmark or the relative-camera-pose hint.
- `*_failed.jsonl` is the drop bucket — rows where the LLM still produced the wrong letter after one stricter retry. Spot-check these for systematic prompt bugs vs. genuinely hard rows.
